# Interop lab: ID-JAG interoperability checks on PingFederate

Run on 2026-10-19 against the kit's PingFederate 13.1.3 (`https://pf.example.invalid`). The ID-JAG was minted by a
real token exchange (a refresh token from a pi.flow sign-in as the exchange client `id-jag-kit`), then redeemed at the
other server with the RFC 7523 JWT bearer grant. `pingfederate/configure-interop-targets.js` creates the two SP
connections used (separate from the kit's own, `--remove` deletes them).

| Target | Result |
|---|---|
| **Authplane 0.2.3** (AGPL, an unmodified container run separately; `authplane/authserver:0.2.3`) | **Accepts it.** Redeemed for an `at+jwt` (scope `read`, `act.sub` = our issuer). |
| **motd.xaa.rocks** (the public xaa.rocks demo resource) | **Refuses it:** `HTTP 400 invalid_grant: The JWT header is missing the 'kid' property` |
| **xaa.dev hosted resource AS** (`auth.resource.xaa.dev`, Okta's sandbox, an outside IdP registered through its "Test your requesting app" API) | **Refuses it at the signature:** `HTTP 400 invalid_grant: JWT signature is invalid` (issuer, audience, client and subject checks passed) |

## Authplane (works)

- Trust: `POST :9001/admin/idps {name, issuer, jwks_uri, audience}`; a client `POST /admin/clients` (jwt-bearer,
  `client_secret_basic`, a non-empty `scope`; the client id is generated by Authplane); a resource; and an XAA policy
  (without one the exchange is `403 access_denied`).
- PingFederate SP connection: entityId = Authplane's issuer, `resourceUris` = the registered resource uri, scope `read`,
  and the ID-JAG's `client_id` pinned to Authplane's generated client id (Authplane requires it to equal the
  authenticated client).
- Header of our ID-JAG: `typ oauth-id-jag+jwt`, `alg RS256`, **`x5t` and no `kid`**. Authplane accepts it: with no `kid`
  it tries the keys in the issuer's JWKS.
- Refusals, as the draft requires: replay of the same `jti` -> `400 invalid_grant` ("already been used"); wrong client
  secret -> `401 invalid_client`; a resource that is not the one in the assertion -> `400 invalid_scope`; an ID-JAG
  addressed to someone else (`aud` motd) -> `400 invalid_grant` ("audience does not match").

## motd.xaa.rocks (refused: a PingFederate limitation)

motd's token endpoint verifies the signature by `kid` and refuses a header without one. PingFederate's ID-JAG header
has only `typ`, `alg` and `x5t`. Probed on the SP connection (the only place the signing is configured): the flags
`includeCertInSignature` and `includeRawKeyInSignature` do not change the header (the second is also refused with
HTTP 422 on its own), and the signing key is the key PingFederate's own JWKS publishes. So a consumer that requires
`kid` cannot validate a PingFederate 13.1.3 ID-JAG. No setting was found that adds it.

What would unblock it: PingFederate emitting `kid` in the ID-JAG header (the JWKS documentation says PingFederate
adds the key id when it signs a JWT; it does not for ID-JAGs), or a signing proxy in front. Needs a PingFederate
change or a support case; not something the kit can fix.

## Repeat it

```
docker compose -p authplane-test --env-file <env with AUTHPLANE_ADMIN_API_KEY, AUTHPLANE_SESSION_SECRET> up -d
node pingfederate/configure-interop-targets.js --ns=<ns> --authplane-client-id=<id Authplane generated>
# mint at PingFederate (audience, resource, scope per target) and redeem; remove everything:
node pingfederate/configure-interop-targets.js --ns=<ns> --remove
```

## Can PingFederate take a SAML assertion as the subject token? (yes)

`tools/saml-spike` (see its README). A signed SAML 2.0 assertion sent as `subject_token` with
`subject_token_type=urn:ietf:params:oauth:token-type:saml2` returns an ID-JAG (`HTTP 200`, `sub` = the assertion's
NameID, `typ oauth-id-jag+jwt`, `x5t` and no `kid`). A tampered signature, the wrong audience, an expired assertion, an
untrusted signing key and an unsigned assertion are each refused with a specific error. The kit's playground still shows
SAML as mock only; a real path is now possible and would use this same processor and exchange policy.

## xaa.dev's hosted resource AS with our PingFederate as the IdP (refused)

Run 2026-10-19. xaa.dev accepts outside IdPs: `POST https://auth.resource.xaa.dev/api/providers {name, issuer}` registers an
issuer (it discovers the endpoints from `/.well-known/openid-configuration`), and `POST /api/clients {client_id,
client_secret}` registers the client. Both are unauthenticated and the registry is shared and global. We registered the
kit's PingFederate and a throwaway client, created an SP connection (`pingfederate/configure-interop-targets.js`,
`--xaa-client-id`, `--xaa-subject`) with audience `https://auth.resource.xaa.dev`, resource `https://api.resource.xaa.dev`,
scope `todos.read`, the `client_id` claim pinned to the registered client and `sub` pinned to a made-up id (so no real
identity goes to a public sandbox), then redeemed with the JWT bearer grant (HTTP Basic and client_secret_post).

Result: `invalid_grant: JWT signature is invalid`. The ID-JAG is valid: Authplane verified the same token against the same
JWKS. The JWKS lists three entries (`aidemopf-idjag`, `aidemopf-idjag_RS256`, `aidemopf-idjag-signing`) with identical
modulus and `x5t`, so choosing among them cannot matter. The header has `typ`, `alg` and `x5t`, no `kid`. xaa.dev's own
rejection log (`GET /api/logs` with `X-User-Email: <the sub>`) gives no more detail. The most likely cause is a key lookup
by `kid` that finds nothing, which is the same root cause as motd.xaa.rocks, reported there as "missing kid". That was a
guess from outside; it is now proven (next section). The test objects were removed afterwards (the provider is deleted; xaa.dev has no delete route for
clients, so the throwaway client record remains).

So of three outside resource servers, one (Authplane) accepts a PingFederate 13.1.3 ID-JAG and two public sandboxes do not.

## Proof: the missing `kid` is the whole problem (2026-10-19)

Same PingFederate, same signing key (`aidemopf-idjag-signing`), same claims, same client, same xaa.dev. Only the JWT header
changed. The token came from a throwaway lab setup (a PingFederate JWT access token manager with `Type Header Value`
`oauth-id-jag+jwt`, `Audience Claim Value` `https://auth.resource.xaa.dev`, a client-credentials client whose id is the client
registered at xaa.dev, and a mapping filling `sub`, `scope`, `client_id`, `resource`). That token manager has an *Include Key
ID Header Parameter* switch, which the ID-JAG token-exchange path does not.

| Header | xaa.dev `/token` (JWT bearer) |
|---|---|
| `typ oauth-id-jag+jwt`, `alg RS256`, **`kid aidemopf-idjag-signing`** | `HTTP 200`, access token issued, `scope todos.read` |
| the same token with *Include Key ID Header Parameter* off (no `kid`) | `HTTP 400 invalid_grant: JWT signature is invalid` |

So xaa.dev and motd.xaa.rocks both look the key up by `kid`; without one they fail (xaa.dev reports it as a bad signature, motd as
a missing `kid`). The lab token is not a token exchange and not an ID-JAG PingFederate issued as one (`issued_token_type` is
an access token), so it only proves the cause; it is not a supported workaround. All lab objects were removed (the token
manager, client and mapping on the kit PingFederate, and the provider at xaa.dev).

`kid` is optional per RFC 7515 4.1.4 and draft-ietf-oauth-identity-assertion-authz-grant-04 only requires `typ`, so this is an
interop gap, not a spec failure.

### Text for a PingFederate support case / enhancement request

> PingFederate 13.1.3, OAuth token exchange, requested_token_type `urn:ietf:params:oauth:token-type:id-jag`. The ID-JAG is
> signed with a key that PingFederate publishes at its JWKS endpoint, but the JWT header contains only `typ`, `alg` and `x5t`:
> there is no `kid`. The JWKS documentation says PingFederate includes the matching `kid` when it signs a JWT, and it does
> for ID tokens (`kid` present for the same key) and for JWT access tokens (switch: Include Key ID Header Parameter). Public
> resource authorization servers that select the verification key by `kid` reject the ID-JAG: motd.xaa.rocks ("The JWT header
> is missing the 'kid' property") and auth.resource.xaa.dev ("JWT signature is invalid"). With the only change being a `kid`
> in the header, the latter accepts the token. Request: emit `kid` in the ID-JAG header for keys published in the JWKS, or add
> an SP-connection signing option for it. No SP-connection signing setting we found (including includeCertInSignature and
> includeRawKeyInSignature) adds it.

### Everything tried to get a native ID-JAG to carry `kid` (none worked)

Run 2026-10-19 on PingFederate 13.1.3, header read after each change. The ID-JAG header is always `typ`, `alg`, `x5t`.

| Tried | Header result |
|---|---|
| SP connection `includeCertInSignature`, `includeRawKeyInSignature` | unchanged |
| RSA-PSS (`SHA256withRSAandMGF1`) | `alg` PS256, no `kid` |
| EC P-256 key (`SHA256withECDSA`) | `alg` ES256, no `kid` |
| `alternativeSigningKeyPairRefs` with a second RSA key, as alternative and as primary | unchanged |
| The exchange client's default access token manager set to a JWT manager with *Include Key ID Header Parameter* on | unchanged: a native ID-JAG is signed by the SP connection, not by an access token manager |

The Admin API (13.1.3.0) `SigningSettings` has only `signingKeyPairRef`, `alternativeSigningKeyPairRefs`, `algorithm`,
`includeCertInSignature` and `includeRawKeyInSignature`; `idJagEnabled` only sets `typ`. The 13.1 to 13.1.3 release notes
and the ID-JAG setup page say nothing about `kid`. Another receiver project reports the same for 13.1.3
(mmcintosh/better-auth-id-jag PR 41: "never sends kid, only x5t").

### Workaround that works: answer the token exchange from a JWT access token manager (not a native ID-JAG)

A real RFC 8693 exchange (refresh token as the subject) whose requested type is an access token can be answered by a JWT
access token manager, which has *Include Key ID Header Parameter*. Per target, on PingFederate:

1. Clone a JWT access token manager (plugin `JwtBearerAccessTokenManagementPlugin`): *Include Key ID Header Parameter* on,
   *Type Header Value* `oauth-id-jag+jwt`, *Audience Claim Value* the target's audience, *Issuer Claim Value* PingFederate,
   *Token Lifetime* 5 (minutes), *Publish Keys to the PingFederate JWKS Endpoint* off (the key is already in the static JWKS,
   and publishing twice fails the key id uniqueness check), *Resource URIs* the target's resource. Extended attributes: `sub`,
   `scope`, `client_id`, `resource`. Plugin ids must be alphanumeric.
2. An access token mapping, context *Token exchange processor policy* (the client's policy), to that manager, filling the four
   attributes (`client_id` is the client registered at the target; pin `sub` for public sandboxes).
3. A client with the token-exchange grant, a secret, and *Restrict to default access token manager* off.
4. Exchange with `requested_token_type=urn:ietf:params:oauth:token-type:access_token`, the subject refresh token, `resource` and
   `audience`. Do not send `scope` unless PingFederate defines it (otherwise `invalid_scope`).

Result: header `typ oauth-id-jag+jwt`, `alg RS256`, `kid aidemopf-idjag-signing`. Redeemed with the JWT bearer grant:

| Target | Result |
|---|---|
| motd.xaa.rocks | `HTTP 200`, access token issued |
| xaa.dev | `HTTP 200`, access token issued, scope `todos.read` |

Limits: `issued_token_type` is an access token, not the id-jag type; PingFederate's ID-JAG validation window and SP connection
checks do not apply; one manager per target (the audience is fixed per manager). A stopgap until PingFederate emits `kid`
natively. All lab objects were removed afterwards.

### In the playground

The Interop panel (pf-as mode) shows motd.xaa.rocks and xaa.dev twice: the native ID-JAG (x5t, no kid; refused) and the
workaround (kid; accepted). `node pingfederate/configure-kid-workaround.js --xaa-client-id=<id>` (the kit's own PingFederate, `PF_ADMIN_URL` set as in `pingfederate/README.md`) creates the token
managers, mappings and the `id-jag-kit-kid` client and writes `INTEROP_KID_CLIENT_ID` / `_SECRET` to the shared settings file; `--remove` deletes them.
